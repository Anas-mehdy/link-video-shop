# Automatic abandoned-cart delivery

## Setup
1. Run `crm-whatsapp-delivery.sql` in Supabase SQL Editor after the existing Salla sync, WhatsApp events and test-send scripts. It is repeatable; initial settings disable sending.
2. Keep incoming Salla and Etisalna n8n workflows published. Keep the tested `ETISALNA_API_ACCESS_TOKEN` and `CRM_WORKER_TOKEN` in Vercel Production. Add `WHATSAPP_AUTOMATION_ENABLED=true`, then redeploy. This server gate alone does not enable customer sending.
3. Create a separate n8n workflow: **Schedule Trigger** every **1 minute** → **HTTP Request**. POST `https://link-video-shop.vercel.app/api/crm-worker?action=whatsapp-delivery`, with credential Header Auth: name `Authorization`, value `Bearer <CRM_WORKER_TOKEN>`. No body is required. Request timeout 55000 milliseconds. Leave Retry On Fail off; review errors and unknown results instead of replaying provider sends. Publish the workflow. One tick claims at most one message; duplicates and concurrent ticks are protected by the database.
4. Open Dashboard → Automations → Automatic cart followup. Verify server readiness, worker's last check and saved settings. Register genuine WhatsApp consent and its source using the consent form for eligible contacts, or prepare a reviewed import of documented consent records. A cart/phone alone is not consent. Existing unsubscribe continues to block even after recording consent.
5. Choose 60–120 minutes. Optional Saudi contact window is 09:00–21:00; disabled by default to preserve the requested one-hour followup at night too. Turning it on defers nighttime messages and can exceed two hours. Confirm actual sending, check Enable and save only when ready to launch. Toggling off stops new claims; it cannot recall a provider call already in flight.

## Behavior and limits
No Salla API call is made by this delivery worker. It reads the locally projected carts/orders. Received unprojected `order.*` or `abandoned.cart*` events block sending (`projection_pending`); fix/replay them via the existing Salla event processor, then resume.

The available activity reference is greatest(cart creation, Salla source update). Source updates can be automatic and are not proof of a browser action. Recent updates after activation enroll carts created long ago; older unchanged carts are not backfilled. Subsequent strictly newer source updates move pending reminders to activity + configured delay. Replaying the same event does not restart the countdown. A cart gets at most one attempt, and a phone is not contacted again within 24 hours across carts. The prior manual test attempt also blocks automatic sending for that same cart. Cart UUID and phone stay matched; no redirect to a fixed test phone occurs in automatic mode.

Before claiming, the worker checks active cart state, consent, unsubscribe, locally received subsequent orders, supported mtjr.at URL, and last activity under 24h. Orders created at or after latest activity count as purchases; recovered cart status independently prevents sending. Recovered/inactive/expired/opted-out and already contacted carts are cancelled. Cancellation or a completed attempt does not auto-rearm the same cart. On disable/re-enable the activation cutoff moves to the new enable time; no paused backlog is sent automatically.

Database claim commits before the external request; a new purchase/unsubscribe can race with a provider call already starting. No cross-system atomic send is possible. A fresh incoming event that is durably pending blocks the claim. Unforwarded provider/store events cannot be checked.

`accepted` means Etisalna returned HTTP 201 with a message ID, not delivery/read confirmation. Provider rejection, malformed responses and timeouts use `unknown`. A crashed `sending` claim becomes `unknown` after two minutes and is never reissued. Do not delete attempts to force a retry before checking the provider conversation. A late successful completion with the same attempt token may finalize an unknown claim. There is no automatic retry without provider idempotency support.

At one message per minute, followup time is a target with scheduler/queue lag; large bursts can delay it. Unknown results, pending projections, missing consent, quiet hours and paused workers also delay or block it. Inspect the newest 100 entries in the dashboard. All tables are private and service-role-only. The provider key and worker token are never returned to the browser. This is cart followup only; post-sale/review campaigns and template authoring remain separate work.
