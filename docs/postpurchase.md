# تجهيز ما بعد البيع تلقائيًا

التشغيل الحالي للمعاينة فقط؛ لا توجد رسائل صادرة أو فحص مخزون دوري.

## المسار الأساسي

1. بعد تشغيل أساس `crm-postpurchase.sql` شغّل `crm-postpurchase-auto.sql` مرة واحدة.
2. افتح `/dashboard#postpurchase` واضغط **تجهيز الكتالوج والربط تلقائيًا**.
3. يجلب الزر المنتجات الحالية بصفحات حتى 60 منتجًا حسب استجابة سلة، ويخزّنها محليًا. الحد الصارم 20 محاولة جلب في الشهر لهذه الميزة، و10 صفحات في ضغطة واحدة. لا إعادة تلقائية عند خطأ أو 429؛ يمكن متابعة الصفحة المحفوظة يدويًا ضمن الحد.
4. يُعاد استخدام الكتالوج المكتمل خلال 24 ساعة؛ الجلب والحفظ لا يعملان بمجرد فتح الصفحة أو من عامل الدقيقة.
5. بعد اكتمال الجلب، تُستخرج الموديلات ونوع الحماية من العناوين والأوصاف والخيارات. لكل منتج مشتَرى يولّد النظام حتى 3 عروض: حماية شاشة، عدسات، وإطار كاميرا؛ عرض واحد لكل نوع من نفس الموديل، مع أولوية للكمية المتاحة ثم ترتيب ثابت بالمعرّف.
6. تراجع فقط الاستثناءات: موديل غير واضح، تعارض في البيانات، خيارات موديل/نسخ غير محسومة، أو بكج يحتاج تأكيد محتوياته. أسماء من الطلبات المحلية وحدها لا تُعتمد بدون مراجعة.
7. التعديلات اليدوية لا تُستبدل بإعادة التحليل؛ القواعد التي أوقفتها يدويًا تبقى متوقفة.

المنتجات المخفية وخدمات التغليف وبعض الملحقات العامة تُستبعد من هذه المرحلة. العروض التلقائية لا تشمل بكجات مختلطة؛ محتويات البكج المشتَرى تُراجع لمنع تكرار أي مكوّن. توفر المنتج وقت جلب الكتالوج ليس ضمانًا لتوفره يوم إرسال العرض؛ فحص المخزون قبل الإرسال يُبنى في المرحلة التالية. لا يحتاج التحليل المحلي خدمة AI مدفوعة أو طلبات جديدة إلى سلة.

عداد 20 طلبًا يخص **جلب الكتالوج لهذا القسم**، ولا يمثل استهلاك التطبيق الكلي أو ميزانية فحص المخزون المستقبلية. الطلبات الفاشلة أو غير المؤكدة تُحتسب ولا تُردّ إلى الرصيد. قفل لمدة دقيقتين يمنع الجلب المتزامن؛ اكتمال الصفحة يُحفظ بمعرّف حجز لمنع تقدم الصفحة مرتين.

## اختبار

`node --test tests/postpurchase-auto.test.js tests/postpurchase.test.js`

يغطي التحليل العربي والإنجليزي والموديلات المختلفة والبكجات والخيارات، طلبًا واحدًا لكل حجز وعدم الإعادة التلقائية، سقف الميزانية وقفل التزامن والصلاحيات الخاصة، وحفظ التعديلات والتوقفات اليدوية.

## تفاصيل أساس المعاينة

هذه المرحلة تعرض العملاء والعروض المقترحة فقط. لا ترسل واتساب، ولا تنادي API سلة، ولا تغيّر عامل تذكيرات السلات.

## التجهيز

1. شغّل `crm-postpurchase.sql` في Supabase SQL Editor. يحتاج جداول الطلبات والعملاء الموجودة، ومزامنة سلة السابقة (`crm_source_at`)، وجدول إلغاء اشتراك واتساب.
2. افتح `/dashboard#postpurchase`.
3. عرّف منتجًا مشتَرى ومنتجًا مكملًا. القائمة المقترحة مستخرجة من الطلبات المحلية لآخر 30 يومًا، وليست جميع منتجات المتجر. يمكن إدخال منتج غير موجود فيها يدويًا.
4. أدخل موديل الجهاز بدقة ومحتويات كل بكج كاملة. عند وجود موديلات مختلفة لنفس المنتج، عرّف كل SKU على حدة؛ المنتج متعدد الموديلات لا يُربط كأنه موديل واحد.
5. أضف قاعدة تربط المنتج المشتَرى بالعرض، ثم راجع المعاينة.

## ما يعمل الآن

- جداول خاصة لا يستطيع anon أو authenticated الوصول إليها مباشرة. الواجهة تعمل عبر API الإدارة المحمي.
- تعديل التعريفات والعروض وإيقاف قواعد المعاينة.
- إعدادات محفوظة: 7 أيام، 11:00 و17:00 و20:00 بتوقيت السعودية، 10 عملاء كحد أقصى، 14 يومًا بين العروض، ميزانية مستقبلية لفحص المخزون 300 طلب شهريًا.
- ملاحظة انتقال الطلبات إلى delivered بعد بدء النظام؛ الساعة تبدأ عند رصد الانتقال محليًا، ولا نقترض تاريخ تسليم سابقًا من تاريخ إنشاء الطلب. السجلات المستوردة بحالة delivered لا تُسجّل كتسليم جديد؛ الطلبات القديمة لا يُفترض لها تاريخ تسليم. التحديث المتكرر لنفس حالة التسليم لا يعيد بدء المؤقت.
- معاينة حتى 200 طلب مسلّم من آخر 30 يومًا، وعرض حتى 100 مطابقة؛ أرقام الصفحة تخص هذه العينة المحدودة.
- استبعاد في المعاينة عند إلغاء الاشتراك أو شراء لاحق أو امتلاك مكوّن من العرض أو اختلاف الموديل أو وجود منتج غير معرّف بالطلب.
- لا نفترض توفر المخزون: المطابقة التي حان موعدها تظهر «فحص المخزون والقالب مطلوب».

## ما يحتاج المرحلة التالية

- مراجعة المنتجات الفعلية والموديلات وSKU ومحتويات البكجات.
- قالب تسويقي سعودي معتمد في Etisalna، بمتغير اسم العميل واسم العرض ورابط المنتج وزر إلغاء الاشتراك. قالب السلة الحالي ورابط mtjr.at للسلة لا يعاد استخدامهما تلقائيًا للمنتجات.
- فحص مخزون المنتجات والنسخ المقترحة فقط قبل الدفعة، مع عداد وميزانية محدودة؛ لا فحص كل دقيقة ولا استيراد تاريخي.
- طابور إرسال مع قفل ومنع التكرار واحتساب حد الدفعة وفاصل 14 يومًا وإعادة التحقق من الشراء/إلغاء الاشتراك قبل الإرسال.
- إدخال بيانات المرتجعات والشكاوى كإشارات منع موثوقة. لا يوجد في هذه المرحلة كشف تلقائي للشكاوى.
- دمج عامل الدقيقة الموجود مع قواعد عادلة بين تذكيرات السلة وما بعد البيع، وإرسال واحد في الدقيقة.
- حالات قبول المزود والتسليم الفعلي منفصلة، وقياس النقر والشراء اللاحق بعد إعداد التتبع.

حتى تكتمل هذه المتطلبات لا يوجد زر لتفعيل الإرسال، ولا يمكن تفعيله عبر API هذه الصفحة.

## تحقق محلي

`node --test tests/postpurchase.test.js`

تغطي الاختبارات تشغيل SQL مرتين، التوقيت، محتويات البكجات، الموديل، إلغاء الاشتراك، شراء لاحق، المعرفات والروابط، منع الوضع الفعلي، والصلاحيات الخاصة.


### تحسين التصنيف المحلي
الإطار المعدني الجانبي يدخل ضمن حماية جسم الجوال (case)، بينما إطار الكاميرا مستقل. عبارات عدم التوافق الصريحة في جملة منفصلة لا تسبب تعارض موديل؛ اختلاف التوافق الإيجابي يبقى للمراجعة. إعادة التحليل تستخدم الكتالوج المحفوظ ولا تستدعي سلة، ولا تحتاج SQL إضافيًا.
